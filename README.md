# Fedora Doctor

Локальное графическое приложение для консервативной диагностики Fedora Linux. Целевая среда — Fedora 44, KDE Plasma 6 и Wayland; при каждом запуске ОС, ядро, архитектура и графическая сессия определяются заново. Приложение также может запускаться на других Linux-системах, но состав доступных проверок там зависит от установленных утилит.

## Что умеет

- Собирает сведения о systemd, DNF5, CPU, памяти, датчиках, процессах, GPU/NVIDIA, накопителях, Btrfs, сети, журнале и загрузке.
- Разносит сбор данных и правила анализа; выводы содержат серьёзность, статус наблюдения, доказательства, объяснение, уверенность, рекомендации и команды.
- Ищет ограниченные взаимосвязи (например, ошибки NVIDIA вместе с сообщениями KWin), помечая их вероятными, а не причинно доказанными.
- Выполняет сбор в рабочем потоке Qt, показывает результаты по компонентам, даёт фильтр серьёзности, сохраняет историю в каталоге пользовательских данных и экспортирует JSON/HTML.
- Запускается без root. Команды вызываются с аргументами без shell, с таймаутом и ограничением вывода. Недоступные команды отображаются как отсутствующие.

В этой первой версии SMART и часть аппаратных сведений доступны только если соответствующие утилиты установлены и имеют права чтения. Приложение не запрашивает пароль и не повышает привилегии. Команда `sudo smartctl ...` в карточке — только копируемая подсказка для пользователя. `dmidecode` часто недоступен без root. Стресс-тесты, ремонт, scrub, fsck, изменения сети, служб, ядра, GRUB, пакетов и настроек не выполняются.

## Установка на Fedora

Установка создаёт Python virtualenv в `~/.local/share/fedora-doctor` и ярлык KDE в `~/.local/share/applications`; системные файлы не меняются:

```bash
./scripts/install.sh
```

Затем запустите `fedora-doctor` из меню приложений или терминала. Для разработки:

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -e .
python -m app.main
```

Если в уже установленном приложении не появились новые функции, обновите локальный пакет командой `./scripts/install.sh`. Установщик принудительно переустанавливает файлы проекта, даже если версия в metadata не изменилась. Для полной пересборки виртуального окружения используйте `./scripts/install.sh --clean`; удаляется только `~/.local/share/fedora-doctor/venv`, а история диагностики и `reliability.sqlite3` сохраняются. После установки полностью закройте старое окно и запустите `fedora-doctor` заново.

Если системе не хватает опциональных диагностических утилит, установите выбранные вручную после проверки списка: `smartmontools`, `lm_sensors`, `pciutils`, `util-linux`, `btrfs-progs`, `vulkan-tools`, `glx-utils`. Приложение специально не устанавливает их автоматически. NVIDIA-команды доступны при наличии проприетарного драйвера.

## Разработка и проверка

```bash
pip install -e '.[dev]'
QT_QPA_PLATFORM=offscreen pytest -q
QT_QPA_PLATFORM=offscreen python -c 'from PySide6.QtWidgets import QApplication; from app.main import MainWindow; a=QApplication([]); w=MainWindow(); print(w.windowTitle())'
```

Коллекторы находятся в `app/collectors`, анализ — в `app/analyzers`, модели — в `app/models.py`, UI — в `app/main.py`, сериализация — в `app/reports`. Все вызовы ограничены таймаутами. Журнал выбирается через `journalctl` с ограниченным числом строк; полный журнал не сохраняется без запроса.

## Безопасность и ограничения

Запуск диагностики может читать журналы и метаданные, а также кратко измерить CPU за 0,3 секунды. Права обычного пользователя могут скрыть часть данных; отсутствие данных не означает отсутствия неисправности. Оценки уверенности — эвристические значения правил, не статистическая вероятность. Перед выполнением скопированной команды изучите её; диагностические команды могут включать чтение от root. Никаких исправлений автоматически не запускается.

История содержит системные сведения и фрагменты журналов, доступные коллекторам, и хранится локально в каталоге `fedora-doctor` пользователя. JSON/HTML отчёты могут включать имена процессов, устройств и сообщения журналов: перед отправкой третьим лицам проверьте их содержимое.

## Мониторинг надёжности и расследование инцидентов

Во вкладке **«Надёжность»** доступны разовый сбор журналов, метаданных core dump и снимка производительности, а также непрерывный сбор, который включается и останавливается кнопками. Непрерывный сбор работает только пока открыт Fedora Doctor: системная служба и фоновый запуск после выхода не устанавливаются. Интервал метрик настраивается от 10 до 300 секунд; срок хранения и предельное число точек можно изменить в этой вкладке.

События читаются из `journalctl` и метаданных `coredumpctl list`; обычное завершение процесса не считается сбоем. Для SIGSEGV/SIGABRT, OOM, ошибок ядра и графической сессии сохраняются доступные время, процесс/PID, сигнал, источник и строки журнала. Для получения stack trace выберите группу падений и нажмите **«Получить stack trace…»**. Приложение спросит согласие, затем выполнит `coredumpctl info` в рабочем потоке и сохранит только найденный текст стека. Полный дамп памяти не выгружается и не сохраняется приложением.

SQLite-база `reliability.sqlite3` хранится в пользовательском каталоге Fedora Doctor. Миграции используют `PRAGMA user_version`; ротация удаляет старые строки по сроку хранения и ограничивает временной ряд, инциденты и изменения. Собираются CPU, RAM, swap, доступные температуры, счётчики Disk I/O и сети, load average, а для NVIDIA или совместимого DRM sysfs — доступные GPU/VRAM метрики. Отсутствующие датчики остаются пустыми.

Система изменений сравнивает выбранные версии RPM (ядро, NVIDIA, Mesa, KWin/Plasma и PipeWire), метаданные отдельных системных конфигураций и доступную раскладку экранов KDE. Содержимое конфигурационных файлов не читается. Время установки RPM берётся из RPM metadata; конфигурационные события получают время изменения файла. Полный список DNF transaction ID и файлов транзакций пока не собирается. В расследовании временная близость и повторяемость показываются как корреляции и кандидаты для проверки, а не как доказанная первопричина.

История надёжности экспортируется отдельно в JSON или автономный HTML. Перед отправкой отчёта проверьте его: он включает журнальные строки, имена процессов/PID, версии пакетов, метаданные системных конфигураций и метрики. Полные дампы памяти и пользовательские файлы в экспорт не включаются.

### Ограничения мониторинга

- Мониторинг не работает после закрытия приложения или выхода из сеанса; события за последние сутки подбираются при следующем открытии, если журналы доступны.
- Доступ к `journalctl`/`coredumpctl` зависит от политики Fedora и пользователя. Недоступность источника показывается отдельно и не трактуется как отсутствие ошибок.
- Core dump даёт только доступные systemd метаданные; stack trace загружается по явному запросу и может отсутствовать без символов отладки или доступного дампа.
- DrKonqi, Flatpak и RPM падения обнаруживаются через журналы и systemd-coredump, если соответствующие записи доступны. Приложение не сканирует пользовательские файлы и не наблюдает напрямую за каждым процессом.
- Зависание процесса не выводится из отсутствия активности; отмечаются только явные сообщения журналов о зависании/неотвечающем процессе.
- Перезагрузка между сессиями мониторинга отмечается как новая загрузка, но приложение не может доказать, что перезагрузка была неожиданной.
- Изменения пакетов и конфигураций собираются ограниченным снимком; события, возникшие и исчезнувшие между опросами, могут быть пропущены. Время метаданных не является доказательством причинности.
- Частота опроса журналов — примерно раз в пять минут при непрерывном мониторинге; метрики пишутся с выбранным интервалом. Сбор не запускается от root.
